**Status:** DRAFT

## Purpose

Define the abstractions for measuring engineering success in Athena. This document is intentionally small and stable — it defines *concepts*, not domain-specific weights.

---

## 1. The Problem

Benchmarks (HumanEval, MBPP) have known answers. Engineering tasks do not.

When a user says "fix this borrow checker error", there is no answer key. Success must be inferred from **multiple independent signals** produced by tools, compilers, tests, git, and the user.

Athena must evaluate tasks it has never seen before, in domains it was not explicitly programmed for.

---

## 2. The Six Concepts

### 2.1 Signal

A **Signal** is a single measurable fact about an execution. Signals are the atomic unit of evaluation.

```
Signal
├── id: String
├── name: String
├── kind: SignalKind     (boolean, numeric, structured, duration)
├── domain: [String]     (optional — which domains this applies to)
└── metadata: JSON       (extensible)
```

Signals are produced by **SignalProviders** — plugins that know how to execute a tool and parse its output.

Examples:

```
Signal { name: "CompilationSuccess",   kind: Boolean,  domain: ["rust", "c", "go"] }
Signal { name: "TestsPassed",         kind: Numeric,  domain: ["*"] }
Signal { name: "ExitCode",            kind: Numeric,  domain: ["*"] }
Signal { name: "UserApproval",        kind: Boolean,  domain: ["*"] }
Signal { name: "LinesModified",       kind: Numeric,  domain: ["*"] }
Signal { name: "ClippyWarnings",      kind: Numeric,  domain: ["rust"] }
```

### 2.2 SignalProvider

A **SignalProvider** is a plugin that produces one or more signals by executing a tool and parsing its output.

```
SignalProvider
├── id()
├── produces() -> [SignalKind]
├── evaluate(ctx) -> Result<[SignalResult]>
└── confidence() -> f64
```

Every ToolProvider can also be a SignalProvider. For example:

- `GitProvider` produces `SemanticDiff`, `CommitCreated`, `MergeConflict`
- `CargoProvider` produces `CompilationSuccess`, `TestsPassed`, `ClippyWarnings`
- `NmapProvider` produces `HostDiscovery`, `PortCount`, `StructuredOutput`
- `GenericCommandProvider` produces `ExitCode`, `StdoutLines`, `ExecutionTime`

### 2.3 SignalResult

A **SignalResult** is the output of evaluating a single signal.

```
SignalResult
├── signal_id: String
├── value: SignalValue      (boolean, number, string, structured JSON)
├── confidence: f64         (0.0 - 1.0: how reliable is this measurement?)
├── raw_output: Option<String>
└── metadata: JSON
```

Confidence is important because not all signals are equally trustworthy:
- `ExitCode` from a well-known tool → confidence 0.99
- `UserApproval` implicit (user didn't complain) → confidence 0.30
- `UserApproval` explicit (user said "thanks") → confidence 0.85

### 2.4 Evidence

**Evidence** is a collection of signals from a single execution, with metadata about the source.

```
Evidence
├── source: EvidenceSource
│   ├── academic: HumanEval, MBPP, GSM8K
│   ├── synthetic: Generated tasks, unit tests
│   ├── execution: Tool execution results
│   ├── real_project: Actual user project
│   ├── repeated: Same project, multiple tasks
│   ├── production: Sustained use over time
│   └── human_validation: Explicit human review
├── strength: f64           (derived from source hierarchy)
├── confidence: f64         (aggregate of signal confidences)
├── freshness: DateTime     (when was this collected)
├── signals: Vec<SignalResult>
└── metadata: JSON
```

The `strength` is not a configurable weight — it is derived from the source hierarchy:

```
Academic < Synthetic < Execution < RealProject < Repeated < Production < HumanValidation
```

Athena never hardcodes "Rust projects weight 5". Instead:
- A single `CompilationSuccess` from HumanEval → strength LOW
- A `CompilationSuccess` from the user's actual project → strength HIGH
- 100 `CompilationSuccess` from the user's project over time → strength MAXIMUM

### 2.5 Evaluation

**Evaluation** is the process of collecting signals from a task execution and producing an **EngineeringReport**.

```
EngineeringEvaluator
├── register(provider: SignalProvider)
├── evaluate(task, context) -> EngineeringReport
```

```
EngineeringReport
├── outcome_score: f64      (0.0 - 1.0: did the task succeed?)
├── quality_score: f64      (0.0 - 1.0: how well was it done?)
├── reliability: ReliabilityMetrics
├── coverage: CoverageMetrics
├── evidence: Vec<Evidence>
└── confidence: f64
```

#### Outcome Score vs Quality Score

| Aspect | Outcome Score | Quality Score |
|--------|---------------|---------------|
| What it measures | Did it work? | How well was it solved? |
| Typical signals | CompilationSuccess, TestsPassed, ExitCode | LinesModified, ClippyWarnings, ArchitecturePreserved, DiffMinimality |
| Range | 0.0 (failed) or 1.0 (succeeded) | 0.0 (sloppy) to 1.0 (elegant) |
| Deterministic | Yes (exit codes, test results) | Heuristic (diff analysis, tool warnings) |

#### ReliabilityMetrics

```
ReliabilityMetrics
├── success_rate: f64       (over N executions)
├── variance: f64           (score variance across runs)
├── timeout_rate: f64       (how often does it time out?)
├── crash_rate: f64         (how often does the runtime crash?)
├── tool_failure_rate: f64  (how often do tools fail?)
└── regression_rate: f64    (how often does it break what worked?)
```

#### CoverageMetrics

```
CoverageMetrics
├── domains_tested: Vec<String>   ("rust", "python", "networking", ...)
├── domains_total: usize          (how many Athena supports)
├── coverage_pct: f64             (domains_tested / domains_total)
├── signals_per_domain: HashMap   (how many signals per domain)
└── tasks_per_domain: HashMap     (how many tasks per domain)
```

## 3. The Pipeline

```
User Task
    ↓
Agent executes
    ↓
EngineeringEvaluator
    ↓
  for each registered SignalProvider:
    provider.evaluate(ctx) → Vec<SignalResult>
    ↓
Aggregate signals into Evidence
    ↓
Compute Outcome Score + Quality Score
    ↓
Compute Reliability (from history)
    ↓
Compute Coverage (from history)
    ↓
EngineeringReport
    ↓
Persist to Capability Database (.state/models/<id>/)
```

---

## 4. Design Principles

1. **Signals are plugins.** Athena never hardcodes "rustc --version". It registers SignalProviders that know how to run tools and parse output.
2. **No domain-specific weights.** The system never says "Rust = 0.30". Strengths are derived from the EvidenceSource hierarchy, not from arbitrary numbers.
3. **Confidence is first-class.** Every signal carries its own confidence. Aggregate confidence reflects signal quality, not just quantity.
4. **History matters.** Reliability and Coverage come from accumulated evidence, not single runs.
5. **Separation of concerns.** ToolProviders produce signals. SignalProviders know how to evaluate. The EngineeringEvaluator aggregates. The Capability Database stores. Each has one job.

## 5. Relationship to Existing Code

| Existing | Becomes |
|----------|---------|
| `ValidationResult` (benchmark.rs) | A specific kind of `SignalResult` (for benchmarks with known answers) |
| `resolve_validator()` | A `SignalProvider` registry |
| `CertificationReport` (benchmark.rs) | Extends to include `EngineeringReport` fields |
| `ExperimentEntry` (benchmark.rs) | Extends to include evidence, coverage, reliability |
| `ResearchDatabase` (benchmark.rs) | Refactored to `.state/models/<id>/` model-based storage |

---

## 6. What This Enables

1. **Any domain, any tool.** Add a SignalProvider for a new tool, and Athena can evaluate tasks in that domain.
2. **Honest uncertainty.** If no signals are available for a domain, the Engineering Score defaults to 0 and Confidence drops. Athena never pretends to know what it doesn't.
3. **Improvement over time.** Every successful execution adds evidence. Reliability and Coverage grow organically.
4. **Quality measurement.** The Outcome/Quality split means Athena can distinguish between "it compiles" and "it's a well-engineered solution."
5. **Comparability.** Two models can be compared not just by "did they pass HumanEval?" but by "how well do they solve real engineering tasks, across how many domains, with how much consistency?"
