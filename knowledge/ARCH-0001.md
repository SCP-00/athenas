# Athena V2 Architecture — Engineering Capability Platform

> **Architectural Decision Record** documenting the shift from compiler-centric to certification-centric architecture, and from tool collection to engineering platform.

---

## 1. Executive Summary

Athena is no longer a documentation compiler, a benchmark suite, a runtime wrapper, or another coding agent.

Athena is becoming an **Engineering Capability Platform**:

> Given any hardware, any runtime, any model, any project — produce the highest engineering capability possible and prove that improvement scientifically.

This document defines the architecture for V2: the subsystems, their interfaces, the data flow between them, and the implementation roadmap prioritized by **engineering capability delivered** rather than features implemented.

## 4. Runtime Plugin Ecosystem

### 4.1 Current Runtime Trait

```rust
pub trait Runtime: Send + Sync {
    fn name(&self) -> &str;
    fn load_model(&mut self, model_path: &Path) -> anyhow::Result<()>;
    fn complete(&self, prompt: &str, params: &InferenceParams) -> anyhow::Result<InferenceResult>;
    fn unload(&mut self) -> anyhow::Result<()>;

```

### 4.2 Required Extension

The trait must be extended with **capability metadata** so the system can auto-select:

```rust
pub trait Runtime: Send + Sync {
    fn name(&self) -> &str;
    fn load_model(&mut self, model_path: &Path) -> anyhow::Result<()>;
    fn complete(&self, prompt: &str, params: &InferenceParams) -> anyhow::Result<InferenceResult>;
    fn unload(&mut self) -> anyhow::Result<()>;
    
    // NEW: Capability negotiation
    fn capabilities(&self) -> RuntimeCapabilities;
    fn is_available(&self) -> bool;
    fn estimated_vram_gb(&self) -> f64;
}

pub struct RuntimeCapabilities {
    pub streaming: bool,
    pub tool_calling: bool,
    pub embeddings: bool,
    pub structured_output: bool,
    pub vision: bool,
    pub reasoning_tokens: bool,
    pub function_calling: bool,
    pub image_generation: bool,
    pub local: bool,        // runs locally
    pub offline: bool,      // no internet needed
    pub max_context: usize,
    pub max_batch: usize,
}
```

### 4.3 Runtime Implementations Plan

| Runtime | How to Automate | Priority | Effort |
|---------|----------------|----------|--------|
| **LlamaServerRuntime** | Subprocess `llama-server` + HTTP client on random port | **DONE** | — |
| **MockRuntime** | In-memory deterministic responses | **DONE** | — |
| **OllamaRuntime** | Launch `ollama serve` → REST API at `localhost:11434` | **HIGH** | 2 days |
| **OpenAIRuntime** | OpenAI-compatible HTTP API (configurable endpoint) | **HIGH** | 1 day |
| **LMStudioRuntime** | Launch `lms` daemon → REST API at `localhost:1234` | **MEDIUM** | 2 days |
| **GrokRuntime** | Subprocess `grok --prompt` + `--format json` | **MEDIUM** | 2 days |
| **vLLMRuntime** | Subprocess `python -m vllm.entrypoints.openai.api_server` | **LOW** | 2 days |
| **MLXRuntime** | Apple Silicon only — Python subprocess | **LOW** | 3 days |

### 4.4 Runtime Auto-Detection

The `RuntimeRegistry` should implement:

```
ath doctor
  → detect which runtimes are installed
  → detect which runtimes can load the available models
  → recommend best runtime for current hardware

ath run
  → auto-select runtime based on model file extension and available backends
  → .gguf → try llama.cpp or Ollama
  → no extension → try Ollama or OpenAI
  → remote URL → try OpenAI
```

### 4.5 Capability Negotiation

When the user requests a capability (e.g., `--capability tool-calling`), Athena should:

1. Query all available runtimes for their capabilities
2. Filter to those supporting the requested capability
3. Rank by: locality (local > remote) > speed > vram efficiency
4. Select the best match
5. Report the decision

### 4.6 API Key & Cost Management for Cloud Runtimes

Cloud runtimes (Grok, OpenAI, Anthropic) require API key management and cost tracking:

```rust
pub struct CloudRuntimeConfig {
    pub api_key: Option<String>,
    pub api_base: String,
    pub model: String,
    pub max_cost_per_session: f64,
    pub rate_limit_rpm: u32,
}
```

- API keys stored in `~/.athenas/config.toml` (not in git)
- Cost tracking integrated into ResearchDatabase
- Rate limiting configurable per runtime
- Athena should prefer local runtimes when the requested capability is available locally
- Cost-per-query should appear in certification reports for cloud runtimes

## 5. Knowledge Engine V2

### 5.1 Current State

```

```

### 5.2 Required Providers

| Provider | Source | Priority | Notes |
|----------|--------|----------|-------|
| man | `man <topic>` | DONE | Reference implementation |
| python-docs | docs.python.org | HIGH | Structured HTML |
| rust-docs | doc.rust-lang.org | HIGH | JSON-based |
| cargo-doc | `cargo doc --open` local | MEDIUM | Local HTML |
| npm | npm registry API | MEDIUM | JSON structured |
| pypi | PyPI JSON API | MEDIUM | JSON metadata |
| web-search | DuckDuckGo / SearXNG | MEDIUM | Unstructured HTML |
| LSP | language server protocol | LOW | Structured |
| --help | `<cmd> --help` | MEDIUM | Text parsing |

### 5.3 Provider Architecture

Each provider should implement **four methods** — the trait already exists:

```rust
pub trait KnowledgeProvider {
    fn id(&self) -> &str;
    fn discover(&self, query: &str) -> Result<Vec<KnowledgeSource>, String>;
    fn fetch(&self, source: &KnowledgeSource) -> Result<RawKnowledge, String>;
    fn validate(&self, raw: &RawKnowledge) -> Result<ValidationReport, String>;
    fn normalize(&self, raw: RawKnowledge) -> Result<KnowledgeIR, String>;
}
```

The compiler (compile_ir_to_pack) is already generic — no changes needed.

### 5.4 Web Search Architecture

Investigated: Grok CLI uses `search_web` tool via xAI API. Claude Code uses web tool internally. OpenHands uses browser tools.

**Athena's approach**: Build a `WebSearchProvider` that:

1. Sends query to **SearXNG** (self-hosted, privacy-respecting, offline-capable)
2. Falls back to **DuckDuckGo** (no API key needed) if SearXNG unavailable
3. Falls back to a **configured search backend** (Brave, Tavily, etc.)
4. Reports "No web search available" if no backend is reachable
5. Fetches top N results
6. Strips HTML to text
7. Deduplicates
8. Summarizes each result using local LLM
9. Compiles into Knowledge Pack format

**Bootstrap consideration**: Summarization requires an LLM. If no local LLM is available yet (fresh install), the provider should return raw text without summarization rather than failing.

The key insight: **Web search should feed the compiler, not the prompt.** This allows caching, versioning, and reproducibility.

## 6. Memory Subsystem Architecture

### 6.1 Research Summary

After investigating the current landscape (July 2026), the memory architectures form a clear hierarchy:

| System | Type | Strength | Best For |
|--------|------|----------|----------|
| **Mem0** | API-based memory layer | Multi-level (user/session/agent), hybrid search, Apache 2.0 | General agent memory |
| **Letta (MemGPT)** | OS-inspired virtual memory | Memory blocks, archival storage, recall search, agent-driven context management | Long-running agents with bounded context |
| **Zep + Graphiti** | Temporal knowledge graph | Entity tracking over time, enterprise scale | Complex relationship memory |
| **LangMem** | LangChain module | Tight LangGraph integration, prompt self-optimization | LangGraph-based agents |
| **LightRAG** | Lightweight graph RAG | Fast, low token cost, incremental updates, local-friendly | Efficient knowledge retrieval |
| **GraphRAG (Microsoft)** | Heavy graph RAG | Multi-hop reasoning, global summarization | Deep research (compute-heavy) |
| **RAPTOR** | Recursive tree RAG | Narrative arc preservation, hierarchical summarization | Long document understanding |

### 6.2 Proposed Athena Memory Architecture

**Do NOT implement a full memory system from scratch.** Instead, use existing open-source systems behind a unified `MemoryEngine` trait:

```
MemoryEngine
  │
  ├── Working Memory (current session context)
  │   └── In-memory ring buffer, auto-compaction
  │
  ├── Project Memory (per-repository knowledge)
  │   └── Mem0 or LightRAG backend
  │       └── Indexed by project path, git commit
  │
  ├── Experience Memory (past workflows & outcomes)
  │   └── ResearchDatabase (already exists!)
  │       └── Experiment entries → capability-over-time queries
  │
  └── Knowledge Memory (compiled documentation)
      └── Knowledge Packs (already exists!)
          └── Provider-generated, versioned, cached
```

### 6.3 MemoryEngine Trait

```rust
pub trait MemoryEngine: Send + Sync {
    fn id(&self) -> &str;
    
    /// Store information in memory
    fn store(&mut self, key: &str, value: &str, level: MemoryLevel) -> anyhow::Result<()>;
    
    /// Retrieve relevant memories
    fn retrieve(&self, query: &str, level: MemoryLevel, limit: usize) -> anyhow::Result<Vec<MemoryEntry>>;
    
    /// Summarize/compact memories to stay within context budget
    fn compact(&mut self, target_tokens: usize) -> anyhow::Result<CompactionReport>;
    
    /// Clear session-level memory (preserve project and experience)
    fn clear_session(&mut self) -> anyhow::Result<()>;
}

pub enum MemoryLevel {
    Working,     // Current session (ephemeral)
    Project,     // Per-project (persistent across sessions)
    Experience,  // Past workflows (read-only queries)
    Knowledge,   // Compiled documentation (read-only queries)
}

pub struct MemoryEntry {
    pub id: String,
    pub content: String,
    pub level: MemoryLevel,
    pub timestamp: String,
    pub source: String,       // e.g., "session", "benchmark", "knowledge-pack"
    pub relevance_score: f64, // 0.0 - 1.0
}
```

### 6.4 Auto-Compaction Strategy

Adapted from Claude Code's approach:

1. **Working Memory**: Ring buffer of last N exchanges (default N=20). When full, oldest entries are summarized into a single "context summary" entry.
2. **Project Memory**: Stored as key-value pairs. Auto-compacted when total exceeds 8K tokens. Uses Mem0's consolidation strategy.
3. **Compaction Trigger**: Before each inference call, if total memory > target_context_tokens * 0.8, run compaction.

Today: `ath workspace create <pack-id>` — requires a pre-existing YAML pack.

What we need: `ath env init` — auto-discovers everything.

  │   └── Generate tool availability map
  │
  ├── 3. Detect Runtime
  │   ├── Check: llama-server, ollama, lms (LM Studio), grok, vllm

  │
  ├── 4. Build Knowledge
  │   ├── For each detected language, run knowledge provider (man, docs, etc.)
  │   ├── Generate Knowledge Pack with:
  │   │   ├── Language syntax & best practices

  │   │   ├── Common errors & solutions

### 7.3 Aider-Inspired Repository Mapping

Aider's key innovation is the **repository map** — a compressed summary of the codebase's symbols. Athena should implement similar functionality:

```rust
pub fn build_repo_map(project_root: &Path, max_tokens: usize) -> RepoMap {
    // 1. Use tree-sitter to parse all source files
    // 2. Extract: classes, functions, types, traits, modules
    // 3. Build dependency graph between files
    // 4. Rank symbols by importance (dependency count)
    // 5. Prune to fit within max_tokens budget
    // 6. Return structured summary
}
```

This becomes part of the workspace's system prompt.

## 8. Agent Loop Architecture

### 8.1 When to Build

**Not yet as a production feature.** But a **minimum viable agent spike** is feasible now with existing infrastructure:

The current L0-L3 certification pipeline already includes:
- Executor trait (prepare → execute → cleanup)
- Validator trait (check output correctness)
- ResearchDatabase (record results)

A minimal agent loop (plan → execute → validate → correct → repeat) could be implemented as:
- A new BenchmarkLevel (L4) that wraps L0-L3 in an iterative loop
- Using the existing Executor + Validator infrastructure
- No new memory system required (working memory in prompt is sufficient)

**Recommended approach**: Build the full agent loop (Section 8.2) during V2.3, but implement an **experimental L4 spike** during V2.1 as a BenchmarkRunner that exercises the plan→execute→validate→correct cycle. This validates the architecture early without blocking Environment Builder.

**Full agent loop production requirements:**
1. ✅ Knowledge Engine
2. ✅ Benchmark Engine
3. ✅ Validation Infrastructure
4. ✅ Hardware Detection
5. 🟡 Runtime Ecosystem (in progress)
6. 🔴 Memory System
7. 🔴 Tool Engine
8. 🔴 Environment Builder

### 8.2 Design Principles (for when we build it)

Based on research of Aider, OpenHands, Claude Code, and Grok CLI:

1. **Plan → Execute → Observe → Correct** cycle
2. **Grounded reflection** (use execution results, not self-critique)
3. **Tool-calling via MCP** (interoperable, not proprietary)
4. **Iteration caps** (max 3-5 attempts per task)
5. **Sub-agent delegation** for parallel exploration tasks
6. **Event-sourced state** (OpenHands approach — deterministic replay)

### 8.3 Model Context Protocol (MCP) Integration

MCP is becoming the standard for tool definition and discovery. Athena should implement MCP support using the `rmcp` Rust SDK:

```toml
# Cargo.toml
rmcp = "0.8"  # Official Rust MCP SDK
```

**MCP Clients (Athena connects to these):**

- File system access
- Terminal/shell execution
- Debugger (gdb, lldb, delve)
- Web search
- Package registries (crates.io, PyPI, npm)
- Docker/Podman
- Database query
- Git operations

#### Athena as MCP Host (exposing internal capabilities)
Athena exposes its subsystems as MCP servers so external agents (Aider, Claude Code, OpenHands) can consume them:

- **Knowledge Pack queries** — "What Knowledge Packs are available for Rust?"
- **Experiment database queries** — "What was the best configuration for HumanEval?"
- **Model certification history** — "Show certification trend for Qwen 4B"
- **Hardware capability reporting** — "What GPU does this machine have?"
- **ath certify execution** — "Run certification for model X on benchmark Y"

This positions Athena as a **backend for other engineering agents**, increasing its utility beyond its own CLI.

**Timeline**: MCP client in V2.1 (enables tool ecosystem). MCP host in V3.0 (mature enough for external consumption).

## 9. Automatic Optimization Engine

### 9.1 What to Optimize

| Parameter | Current | Goal | Method |
|-----------|---------|------|--------|
| Context size | User-specified (default 32K) | Auto-tested | Binary search for maximum without OOM |
| Thread count | User-specified | Auto-tuned | Benchmark 1, 2, 4, 8, 16 threads |
| KV cache quant | User-specified | Auto-detected | Use q8_0 if VRAM constrained |
| Batch size | Fixed (512) | Auto-sized | Scale based on prompt length |
| GPU layers | All | Auto-calculated | `llama-fit-params` approach |
| Quantization | User-selected | Recommended | Based on VRAM / model size ratio |
| Sampling params | Default | Auto-tuned | Bayesian optimization over task performance |
| Knowledge pack | User-specified | Auto-selected | Based on project detection |

### 9.2 `ath optimize` Command

```
ath optimize [--model <path>] [--runtime <id>] [--benchmark <id>]
  │
  ├── 1. Profile hardware (CPU, GPU, RAM, VRAM, bandwidth)
  ├── 2. Generate candidate configurations (grid or Bayesian)
  ├── 3. For each candidate:
  │   ├── Load model with config
  │   ├── Run benchmark (1-3 representative tasks)
  │   ├── Record: TTFT, TPS, VRAM used, success/failure
  │   └── Unload model
  ├── 4. Find Pareto frontier (best speed vs lowest resources)
  ├── 5. Recommend default configuration
  └── 6. Save as profile in .state/profiles/
```

## 12. Design Principles (Updated)

1. **Everything is a compiler.** Input → IR → validation → compilation → artifact. Applied to documentation, knowledge, benchmarks, environments.

2. **Everything is reproducible.** Every experiment has an ID, git commit, version string, and complete metadata.

3. **Everything is measurable.** Every subsystem has a capability metric. No feature is added without a way to measure its impact.

4. **Knowledge is generated, not shipped.** Sources are truth. Knowledge Packs are compiled artifacts. Artifacts are disposable.

5. **The model is replaceable; the environment is not.** Athena's value is in what it provides AROUND the model — knowledge, tools, workspace, memory — not in the model itself.

6. **Capability is the primary metric.** TTFT, TPS, and latency are secondary diagnostics. The question is: "Does this help the model solve engineering problems?"

7. **Athena does not distribute knowledge; it distributes the ability to discover, verify, build, optimize, and reuse knowledge.**
