# Engineering Graph — Single Source of Truth

> The Environment Builder does not create files. It creates an **Engineering Graph**. Everything else — workspaces, knowledge packs, runtime selections, memory, benchmarks — is a **projection** of that graph.

---

## 1. Why a Graph

**Current state**: The system maintains parallel state across:
- `knowledge/packs/*.yaml` (Knowledge Pack definitions)
- `.state/project.yaml` (project state)
- `.state/experiments/*.json` (experiment database)
- `graph.json` (documentation knowledge graph)
- `athenas.json` (workspace config)

**Problem**: This duplicated state WILL diverge. The documentation graph knows about CONST-0001. The benchmark knows about HumanEval. The hardware detection knows about RTX 3050. Nothing connects them.

**Solution**: A single Engineering Graph where every entity is a node, every relationship is an edge, and everything else is a query.

**Key design decision**: Use a Rust enum (not trait objects) so all node types are known at compile time. This enables pattern matching and compile-time exhaustiveness checks.

```rust
pub enum EngEdge {

    Contains,        // Repository → File, Module → File

    UsesMemory,      // Model → MemoryNode
```

## 4. Incremental Construction

### 4.1 Principle: Event-Sourced, Not Rebuilt

The graph is never rebuilt from scratch for a single change.

Instead:
```
File change detected (inotify, fsnotify, git hook)
        │
        ▼
Parse changed file (Tree-sitter incremental parse)
        │
        ▼
Compute diff: old subgraph ↔ new subgraph
        │
        ├── Nodes added
        ├── Nodes removed (superseded, not deleted — temporal)
        ├── Edges added
        └── Edges removed (valid_until = now)
        │
        ▼
Apply patch to Engineering Graph (Graphiti-style temporal edge versioning)
        │
        ▼
Notify downstream projections (workspace, knowledge, etc.)
```

### 4.2 Temporal Edges

Every edge has:
```rust
pub struct TemporalEdge {
    pub source: String,
    pub target: String,
    pub relationship: EngEdge,
    pub valid_from: String,  // ISO 8601
    pub valid_until: Option<String>,  // None = current
    pub metadata: HashMap<String, String>,
}
```

Queries default to current edges (`valid_until IS NULL`). Historical queries can access past states.

### 4.3 Cold-Start Strategy

The first time `ath env init` runs on a repository, the graph is **fully constructed**:
1. Scan all files (language detection, tool detection)
2. Compute dependency graphs (tree-sitter parse of entry points)
3. Probe runtimes and hardware
4. Build complete Engineering Graph
5. Serialize to disk (see Section 9)

Cold-start cost: proportional to repository size. For a 10K-file monorepo, expect 30-120s. For a typical project (1000 files), < 10s.

After the initial build, **all updates are incremental**. The cache key is the repository fingerprint (file hashes + tool versions + hardware fingerprint).

### 4.4 Incremental Sources

| Source | Update Method | Granularity |
|--------|--------------|-------------|
| File system | inotify/fsnotify watcher | Single file |
| Git | post-commit hook | Changed files |
| LSP | `textDocument/didChange` | Character range |
| Tree-sitter | Incremental parse | AST node |
| Hardware | Polling (every 30s) | Full replace |
| Runtime | Health check polling | Status update |
| User command | Explicit trigger | Arbitrary |

## 5. Artifact Projections

Every artifact is a **read-only query over the graph**. Not a separate file.

```
Engineering Graph
        │
        ├── workspace.yaml
        │    Query: "(Repository) -[ConfiguredAs]-> (Workspace) -[Contains]-> (KP)
        │                      (Model) -[RunsOn]-> (Runtime)"
        │
        ├── summary.md
        │    Query: "COUNT(File) BY Language, COUNT(Model) BY Runtime"
        │
        ├── Knowledge Packs
        │    Query: "(KnowledgePack) -[GeneratedFrom]-> (KnowledgeSource)"
        │
        ├── Runtime Selection
        │    Query: "Runtime -[InstalledOn]-> OS, Model -[UsesGpu]-> Gpu,
        │            Model.parameters_b * 2 < Gpu.vram_gb"
        │
        ├── Optimization Profile
        │    Query: "Model -[EvaluatedBy]-> Benchmark -[Produces]-> Experiment"
        │
        ├── Benchmark Profile
        │    Query: "Benchmark -[Measures]-> Capability, WITH best scores"
        │
        ├── Documentation Graph (graph.json)
        │    Query: "Document nodes + edges (unchanged)"
        │
        └── Tool Registry
             Query: "Compiler ∪ Debugger ∪ Linter ∪ Formatter ∪ TestRunner"
```

**Caching strategy**: Cache the graph, not the artifacts. Artifacts are always regenerable from the graph. The graph is the expensive part — it evolves incrementally.

## 6. Graph Serialization

The Engineering Graph is persisted to disk as `.athena/graph.bin` (Protocol Buffers, inspired by SCIP).

**Why Protobuf**:
- Compact (4-8x smaller than JSON)
- Deterministic (same data → same bytes → cache key works)
- Fast deserialization (no parsing, just memory mapping)
- Schema evolution (new fields don't break old readers)

**Artifact regeneration**: On every `ath env init` or `ath inspect` invocation:
1. Load `.athena/graph.bin` (or cold-start if missing)
2. Apply incremental updates since last load
3. Generate requested artifacts (workspace.yaml, summary.md, etc.) from the graph
4. Save updated graph

The graph is the expensive part. The artifacts are disposable and never cached.

## 7. Query Mechanism

Implementation uses **Rust method calls** on the graph struct:

```rust
impl EngineeringGraph {
    /// All nodes matching type
    fn nodes_by_type(&self, node_type: EngNodeType) -> Vec<NodeRef>;
    
    /// Outgoing edges from a node
    fn outgoing(&self, node: &str, edge: Option<EngEdge>) -> Vec<EdgeRef>;
    
    /// Incoming edges to a node
    fn incoming(&self, node: &str, edge: Option<EngEdge>) -> Vec<EdgeRef>;
    
    /// Traverse graph from starting nodes following path pattern
    fn traverse(&self, start: NodeQuery, path: Vec<EngEdge>, end: NodeQuery) -> Vec<NodeRef>;
}
```

Syntax like `ath inspect --graph "Language(Rust) -[HasKnowledge]-> KnowledgePack"` maps to `traverse(name_eq("Rust"), vec![EngEdge::HasKnowledge], type_eq(EngNodeType::KnowledgePack))`.

Future: custom query language for ad-hoc filtering.

## 7. Updated Priority Order

1. **Engineering Graph** (graph model + incremental construction + persistence)
2. **ath inspect** (graph visualization + debugging queries)
3. **Environment Builder** (detect → graph → project)
4. **Runtime auto-selection** (graph query: runtime + model + hardware)
5. **Knowledge generation** (graph query: language → knowledge pack)
6. **Memory providers** (graph query: workspace → memory namespace)
7. **Optimization engine** (graph query: model + benchmark → best config)
8. **Agent loop** (consumes graph instead of maintaining parallel state)

## 8. Relationship to Existing Code

The existing `graph.rs` builds a `KnowledgeGraph` from markdown documents with `GraphNode` + `GraphEdge`. This is the **documentation projection** of the Engineering Graph.

The Engineering Graph **extends** this concept to include ALL entity types (not just documents), ALL edge types (not just documentation relationships), and **incremental updates** (not just full rebuilds).

The existing `KnowledgeGraph` becomes a **view/query** over the Engineering Graph:

```rust
fn build_knowledge_graph(eng_graph: &EngineeringGraph) -> KnowledgeGraph {
    // Query: select all Document nodes + their edges
    // Project to existing KnowledgeGraph format
    // No parsing needed — all data already in the graph
}
```

**Migration path**: The existing `graph.rs` works exactly as before. The Engineering Graph adds a new layer below it. No existing code breaks.
